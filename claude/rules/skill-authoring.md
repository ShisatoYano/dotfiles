# Skill記述の型

`claude/skills/`配下のSKILL.mdを書く・編集する際の共通の型。既存Skillsから読み取った暗黙の型を明文化したもの。新しいSkillを追加するとき、既存を編集するときの基準にする。

## frontmatter

- `name`: ディレクトリ名と一致させる(kebab-case)
- `description`: 英語。Claude自身がこのSkillを選ぶかどうかの判断材料になるため、トリガー条件(いつ使うか)を明確に書く。他Skillとの委譲関係(何を委譲する/されるか)もここで簡潔に述べる

## 見出し構成

1. H1: Skill名を英語Title Caseで(例: `# Bug Investigation Workflow`)
2. 概要段落: 日本語1段落で、何をするSkillか+他Skillとの関係(委譲・被委譲)を書く
3. `## 前提`: 手順ではなく、作業全体を通して成り立つ制約・前提条件を箇条書きで
4. `## <工程名>`: 番号付き手順。工程名は「原因調査(再現・切り分け)」のように、その工程が何をする段階かが分かる日本語名にする
5. サブワークフローが複数ある(独立して呼び出される入口が複数ある)Skillは、`## サブワークフローN: 日本語名(english-slug)`の形式にする(`daily-task-workflow`/`notion-task-workflow`参照)

## 相互参照の書き方

- 他Skill全体を指す: `` `skill-name` `` (バッククォート、kebab-case)
- 他Skill内の特定セクションを指す: `` `skill-name`の「セクション名」 ``のように、Skill名と「」付きセクション名をセットで書く

## 簡潔さ

- **MUST**: `前提`セクションや汎用的なルールは、簡潔な箇条書きでまとめる。長い前置きや同じ内容の言い換えを繰り返さない
- **MUST**: 手順の中の1ステップに「なぜそうするか」の理由が要る場合は、そのステップの一文に短く埋め込む。理由の説明のためだけに別セクション・別ファイルを作らない
- 汎用的で複数Skillにまたがる原則(承認ゲート等)は`~/dotfiles/claude/rules/`に切り出してよいが、実行手順そのもの(いつ・何を確認するか)は各Skillの手順内に残す(`~/dotfiles/claude/rules/write-approval.md`参照。rules/は自動読み込みされないため、実行を担保する指示は必ずSkill側に置く)。Skillからrules/を参照する際も、Skillはグローバル配置(`~/.claude/skills`へのシンボリックリンク)でどのリポジトリでも呼ばれうるため、相対パスではなく絶対パス(`~/dotfiles/claude/rules/...`)で書く

## サイズの目安

- 1 Skillはおおよそ40〜100行程度を目安にする
- サブワークフローや前提が肥大化してきたら、別Skillへの切り出しを検討する(`pr-workflow`のように、複数の入口を持ちながらも1ファイルに収まっている構成が「まだ1ファイルでよい」の基準線。`pr-workflow`自体は`## サブワークフローN: 名前(slug)`形式ではなく`## <ワークフロー名>`という見出しを使っており、5のサブワークフロー形式は必須ではなく目安であることの一例でもある)
