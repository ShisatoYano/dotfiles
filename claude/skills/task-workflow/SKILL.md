# Task Workflow

タスクを、調査から方針の承認、作業の委譲、受け入れ検証、タスクの記録、成果物の提出まで進める。分業時は司令塔(lead)がこの手順を使い、作業は作業指示書で実装役(worker)に渡す。実装役がいない単独のセッションでは、作業を`task-execution`の手順で自分で行う。流れは作業の種類によらず共通で、種類で変わる部分は`references/task-kinds.md`、タスクの管理場所(Notion・GitHub Issues)で変わる操作は`references/task-sources.md`にまとめてある。テストの手順は`testing-workflow`を使い、Notionへの書き込みは`notion-task-workflow`に委譲する。

## 前提

- コードを書く作業は`~/.claude/CLAUDE.md`の「コーディング」節、原因調査は同「デバッグ・バグ調査」節、一次情報が要る判断は同「フィードバック」節に従う
- 方針の確定・Notionへの書き込み・Issueへのコメントや起票・push・PR作成は、内容を提示して承認を得てから行う(`~/dotfiles/claude/rules/write-approval.md`)
- 対象リポジトリの外から`git`を向けるときは`cd <path> && git ...`ではなく`git -C <path> ...`を使う(`cd`を挟むとリポジトリのhookが実行されうるとしてツール側の確認が挟まるため)
- 司令塔として起動されたセッション(`~/dotfiles/claude/roles/lead.md`の指示がある)なら「分業時」、それ以外は「単独時」の手順を行う。分業時、司令塔は作業ツリーのファイルを書き換えない

## 事前準備

1. タスクの出どころ: `references/task-sources.md`の「出どころの決め方」で、`notion` / `github` / `none`のどれかに決める。以降の「タスク内容」「登録日時」「進捗の記録」「完了」「起票」は、同ファイルの「出どころごとの操作」で読み替える
2. 作業の種類: タスク内容(Notionの`種類`、Issueのラベル、依頼の文面)から、`references/task-kinds.md`の種類のどれかに決める。決めきれなければユーザーに確認する。以降の「調査で確かめること」「完了条件の形」「受け入れ検証の観点」「成果物の出し方」は、同ファイルの種類の節で読み替える
3. リポジトリの最新化確認(リポジトリを触る作業の場合): 作業対象のローカルの各リポジトリ(サブモジュールを含む)について、本流ブランチ名を決め打ちせず`git symbolic-ref refs/remotes/origin/HEAD --short`で確かめ、`git fetch`してローカルの本流が遅れていないか確認する。遅れていれば一覧にしてユーザーに最新化を依頼し(自動では更新しない)、最新になってから次へ進む
4. 前回までの進捗確認(`notion`・`github`の場合): 持ち越しタスクを初見として扱って重複調査をしないよう、`references/task-sources.md`の「前回までの進捗」を読む

## 調査

分業時、ログ追加・テスト追加・再現用の改造など作業ツリーの編集が要る確認は、調査用の作業指示書(「委譲」の2の書式と送り方。「目的」の冒頭に「調査用」と書く)で実装役に頼み、結果を報告で受け取る。

### 不具合以外

1. タスク内容から、目的と求められている成果物を把握する
2. 種類の「調査で確かめること」を確かめる。流用できる既存の実装・文書・スクリプトがあれば先に調べる
3. 曖昧な点や決めきれない判断があれば、方針を立てる前にユーザーに確認する

### 不具合

1. タスク内容から、現象と期待動作を把握する。可能なら現象を再現する
2. 疑わしい箇所を一通り洗い出す。単一の最有力候補に飛びつかず、コード以外の要因(パラメータ・設定・閾値、環境・データ差異)も含める
3. 洗い出した箇所の、タスクの登録日時以降の本流での変更履歴を確認する(`git log --since="<登録日時>" -- <path>`。`none`なら現象に最初に気付いた時期をユーザーに聞いて起点にし、分からなければ直近のリリースやタグを起点にする)。解消済みの可能性が高ければ、テスト(再現手順の再実行、またはユニットテスト)で裏付けを取り、裏付けられたらユーザーに報告して修正はせず、「タスクの記録」へ進む
4. 未解消なら、低コストな確認(ログ追加・部分的な再現実行)で有力な順に絞り込み、実観測で原因を裏付ける。裏付けが取れない場合は、確信度を明示して断定した原因として示さない
5. 候補が誤りと分かったら、洗い出し済みの次の候補に移る。使い切ったら、それまでの結果を踏まえて2から洗い出し直す

## 方針と完了条件の提示・承認

1. 方針を立てる。判断を伴う大きな作業では2〜3案をメリット・デメリット付きで出し、`AskUserQuestion`で選んでもらう。不具合の修正は原因に対して必要最小限にする。順序に決まりがある作業は、進め方(段階と、段階ごとに確かめること)もここで決める(5で完了条件と照合する相手になるため)
2. 影響範囲(呼び出し元・関連機能・依存するもの・既存環境・読者)を確認し、副作用やデグレが起きないか検討する
3. 確認の方針を立てる。コードや設定を変える作業とデータ解析は、`testing-workflow`の「テスト対象・期待結果の確認」で、どこまでの範囲(ユニット/シミュレーション/実機)で何を確かめるかを決める(移行の検証軸・評価の条件・可視化の手段を含む)。評価の条件をユーザーに確認する手順は、実装役には行えないのでここで済ませる
4. コードや設定を変える作業では、先に「壊れたら困ること」(リスク)を3つまで挙げ、それぞれに観測点(何を見れば正しいと言えるか。戻り値だけでなく状態・出力・副作用)と確かめる層(ユニット/シミュレーション/実機)を決める。異常系・境界値を少なくとも1つ含める(テストがGreenになっただけでは何を保証したか分からないため)
5. 完了条件を、種類の「完了条件の形」に沿って「実行して確かめられる形」(コマンドと期待結果、または確かめる手順と基準)で、4のリスクごとに決め、中断条件(どの前提が崩れたら、または何回試して解消しなければ手を止めて報告するか)と合わせる。中断条件が無いと、うまくいかないときに場当たり的な作業を重ねるため。完了条件ごとに、確かめるのに要る実行(コマンド・設定・範囲)も書き、その実行が進め方(段階の順序など)・制約と両立するかを6の承認の前に照合する。両立しなければ完了条件か進め方を直す(実装役はどちらかを優先して進めるしかなくなるため)
6. (不具合なら原因と、)方針・進め方・影響範囲・確認の方針・リスクと観測点・完了/中断条件・成果物の出し方と置き場所(再現用スクリプトなど残すファイルの場所、発表資料の公開/非公開の区分を含む)をユーザーに提示し、承認を得る。分業時は置き場所を指示書の「成果物」で実装役に渡すため、ここで決めておく。PRで出すなら、PRテンプレート(「成果物の提出」の1の探し方)と貢献ガイド(`CONTRIBUTING.md`など)からPRの必須事項(画像・ログの添付、Issueへのリンクの書き方など)を確かめ、作成が要るもの(例: 変更前後の実行結果の画像)を成果物に含める

## 委譲

1. 成果物がリポジトリの変更なら、作業用ブランチが無ければ既存の命名規則で作り、あれば(持ち越しのタスク・Issueにつながったブランチ・調査から戻ってきた場合)それに切り替える(実装役が`git switch -c`をすると既存hookの承認待ちで止まるため、分業時は司令塔が先に作る)
2. 分業時: `ListAgents`で実装役の名前を確かめ、作業指示書を送る。送るたびに`notify_when_idle: true`を付ける(通知は1回きりなので送るたびに付け直す)。指示書を書く段で進め方・完了条件・制約を足したり変えたりしたら、「方針と完了条件の提示・承認」の5の照合をやり直す。指示書は次の書式にする

   ```
   ## 目的
   ## 種類(task-kinds.md の種類名)
   ## 範囲(触ってよいファイルをパスかglobで。触らないもの)
   ## 成果物(何を・どこに出すか)
   ## 進め方(順序に決まりがあるときの段階と、段階ごとに確かめること)
   ## 完了条件(リスクと観測点ごとに、コマンドと期待結果、または確かめる手順と基準)
   ## 確認の方針(移行の検証軸・評価の条件・可視化の手段を含む)
   ## 中断条件(当たったら手を止めて相談)
   ## 制約(守るべき既存の決まり・やってはいけないこと。調査用なら、加えた変更を戻すか残すか)
   ## 報告のタイミング(理解確認・途中報告の節目・長い処理の開始と終了・完了。各報告に次の報告の見込み時刻)
   ```

3. 分業時: 実装役が返す理解を指示書と照らして合否を返し、ずれていれば具体的に直させる。途中の相談には即答し、ユーザーの判断が要るものはユーザーに聞いてから返す
4. 分業時: 報告が届くたびに、想定どおりかの判定を付けてユーザーに伝える。報告に見込み時刻(次の報告、長い処理の終了。延長の報告を含む)があれば、古いタイマーを消し(`CronDelete`)、その時刻に余裕を足した時刻にワンショットのタイマー(`CronCreate`の`recurring: false`)を張り直す。鳴った時点で次の報告が無ければ本人に状況と新しい見込み時刻を聞く(待機中は司令塔も実装役も自分では起きないため)。待機通知は進捗の代わりにせず(実装役は長い処理をバックグラウンドに回した直後にも待機になるため)、届いたのに報告が無いときに手を止めた理由(相談・エラー・報告忘れ)を本人に確かめる合図に限る。実装役の動きが指示と違って見えたら、指示書と照らし、本人に確かめてからユーザーに伝える(指示書の側が両立していないことがあるため)
5. 単独時: `task-execution`の手順で自分で作業・確認まで行う(理解確認と報告は省く)
6. 実装役から完了条件を満たせない・中断条件に当たったという報告が来たら(単独時は自分で当たったら)、「調査」に戻り(不具合なら洗い出し済みの次の候補から)、方針を承認し直す。実装役が残した未コミットの変更は、戻すか残すかを決めて指示する
7. 承認された範囲を超える作業が必要になったら、ユーザーに報告して方針を見直す。範囲外の課題が見つかったら、今のタスクで扱わず、別タスクの下書き(タイトル・内容・見つけた経緯)をユーザーに示して、起票するか確認する(起票先は出どころに従う)
8. その日中に終わらない見込みになったら、「タスクの記録」の1(区切りの判断)に進む

## 受け入れ検証

1. 成果物を自分で確かめ、完了条件を自分で実行・確認する。実装役の報告だけで合格にしない。成果物がリポジトリの変更なら、次の2つも照合する(どちらも実装役の申告だけでは確かめられないため)。`git diff --name-only <ベース>...HEAD`と`git status --porcelain`(コミットに入っていない変更と未追跡ファイルを拾う)の一覧を範囲(分業時は指示書の「範囲」、単独時は承認した方針の範囲)と照らす。範囲外のファイルがコミットに入っていれば不合格にし、範囲外の未コミットの変更は、実装役(単独時は自分)が加えたものかを確かめ、そうなら不合格、そうでなければユーザーの変更とみなして触らない(`~/.claude/CLAUDE.md`の「身に覚えのない変更の扱い」)。同じ差分のテストファイルから削除・skip・期待値の変更を拾い、分業時は報告の「既存テストの変更」と食い違えば、単独時は理由を説明できないものがあれば不合格にする
2. 1つの`general-purpose`サブエージェントにレビューさせる。ブリーフは対象(リポジトリ・ブランチ・ベース、またはファイル)、目的(分業時は指示書の「目的」、単独時は承認した方針の目的。意図との一致を照らすため)、完了条件、種類の「受け入れ検証の観点」に従うこと(直す必要があると言い切れる指摘と、確かめられなかった前提だけを返し、どこにも投稿しない)に限る。コードの場合は、深さを`~/.claude/skills/pr-workflow/references/review-criteria.md`の「深さの判定」で自分が決めてそのモデルを指定し、ブリーフに深さを入れる。自分の結論や推測は渡さない(独立したレビューにするため)
3. 種類が実装・不具合なら、別の`general-purpose`サブエージェントに反証させる。ブリーフは対象、目的、承認したリスクと観測点、「この実装が誤っていることを示す入力・テストを作って実行し、反証できたもの(入力・手順・実行結果)だけを返す。作業ツリーは書き換えず、scratchpadで実行する。そこで動かせないテストはコードと期待結果を返す」に限る。完了条件と実装役の報告は渡さない(実装役に見えていた基準に引っ張られないため)。返ってきたテストコードは、分業時は実装役に足させて実行させる
4. 1で不合格になったら(2・3を待たずに)、または2・3で指摘や反証があれば、分業時は実装役に直させて1からやり直し、単独時は自分で直す。「動かない」「原因はXだ」など否定的な結論は、自分で裏取りしてからユーザーに伝える
5. 実機での確認が確認の方針にあれば、ここで`testing-workflow`の「実機テストフロー」でユーザーに依頼する(レビューの修正で実機確認をやり直さないよう、受け入れ検証の後に行う)

## タスクの記録

1. 区切りの判断(出どころによらず行う): その日中の完了が見込めなければ、区切りの良いところで止め、ここまでの進捗を2の方法で記録したうえで(`none`なら記録は飛ばす)、今日中に続けるか持ち越すかをユーザーに確認する。分業時は区切る前に実装役へ手を止めて`状態: 途中`で報告するよう頼み、今日中に続けるなら「委譲」の3から再開する
2. `notion`・`github`の場合: 作業内容・確認の結果を整理し、出どころの「進捗の記録」で記録する。出どころの「完了」は成果物の出し方で行う時点が変わる。PRで出すなら、`github`はPR本文の`Closes #<番号>`でマージ時に閉じ、`notion`は「成果物の提出」の1でCIがGreenになったのを確かめてから行う。PRを作らない成果物(レポート・ファイル)なら「成果物の提出」の2・3の後で行い、提出するものが無い場合(解消済みと分かった不具合、pushの要らない検証だけのタスク)は記録に続けてここで「完了」を行う。`github`でPRを作らない場合、進捗の記録と完了の結果は1つのコメントにまとめてよい

## 成果物の提出

種類の「成果物の出し方」に従う。

1. PRで出す場合: 変更がコミットされていることを確かめる(分業時は実装役のコミット。単独時で未コミットなら、作業用ブランチが無ければ既存の命名規則で作り、既存のスタイルでコミットする)。PRテンプレートを`git ls-files | grep -i pull_request_template`で探す(GitHubはファイル名の大文字・小文字を区別せず、ルート・`.github/`・`docs/`と`PULL_REQUEST_TEMPLATE/`ディレクトリを認めるため、決め打ちのパスでは見落とす)。あればコメントに書かれた必須事項も含めて従い、無ければ既存のPRのスタイルでタイトル・本文を下書きし、作業内容・確認の結果と、出どころの「PR本文に入れるリンク」を入れる。下書きを提示し、承認を得てからpush・PR作成(`gh pr create`)を行う(PRの作成者はユーザー自身のアカウントになり、Claudeの関与はコミットの`Co-Authored-By`トレイラーで表す)。画像は、下書きの承認時に貼る画像のパスと見出しも示して承認を得て、PR作成の前に`references/github-image-upload.md`の手順でURLにして本文に入れる(作成直後のチェックで落ちないように)。作成後は`gh pr checks <番号> --watch`をバックグラウンドで実行してCIの結果を待つ(CIが無ければその旨を報告に書く)。失敗したらログで原因を確かめ、この変更によるものなら「委譲」の6と同じく「調査」に戻る。Greenになったら、`notion`なら「タスクの記録」の2の「完了」を行う
2. レポートで出す場合: 結論・根拠・確かめられなかった点をまとめ、図表を含むならArtifactにして、結論と判断を求める点はターミナルに残す(`~/.claude/CLAUDE.md`の「応答スタイル」)。再現用のスクリプトなど残すファイルは、承認した置き場所に置いたことを示す。続けて「タスクの記録」の2の「完了」を行う
3. ファイルで出す場合(発表資料など): 置き場所と書き出したファイルのパスを示す。承認時に非公開と決めたものは、公開リポジトリにコミットしない。公開してよいもの(`decks/public/`など)をリポジトリに入れる場合は1のPRで出す。続けて「タスクの記録」の2の「完了」を行う
