# 作業の種類

`task-workflow`と`task-execution`が、作業の種類ごとに読み替える4項目。流れは共通で、ここにある項目だけが変わる。種類を決めきれないとき(例: 実装とドキュメントの両方)は、主な成果物の種類にし、もう一方の観点も受け入れ検証に加える。人が読む成果物(ドキュメント・発表資料・レポート)の受け入れ検証には、`~/dotfiles/claude/rules/writing-style.md`のパターンに当たっていないかも加える。

## 実装(機能追加・改善)

- 調査で確かめること: 実装対象がまたがるリポジトリ・モジュール、流用できる既存の実装や類似パターン
- 完了条件の形: テストのコマンドと期待結果(期待動作の確認と非デグレ)。方針で挙げたリスクと観測点ごとに決める
- 受け入れ検証の観点: `~/.claude/skills/pr-workflow/references/review-criteria.md`の必須観点と、Mustか確かめられなかった前提かを分ける基準(投稿用の書式の決まりは使わない)。ただし「テスト追加の提案は出力しない」は使わず、承認したリスクを確かめるテストが無い・欠けている場合はMustとして返す。加えて、既存テストの削除・skip・期待値の変更が理由なく入っていないか、assertが実行されたことしか見ていない(定義されている・呼ばれた程度の)テストやモックで中身を置き換えたテストで完了条件を満たしていないか
- 成果物の出し方: PR

## 不具合

- 調査で確かめること: `task-workflow`の「調査」の「不具合」の手順(本体に書いてある)
- 完了条件の形: 再現手順の再実行で現象が出ないこと、と非デグレのテスト
- 受け入れ検証の観点: 実装と同じ。加えて、修正が裏付けた原因に対して必要最小限か
- 成果物の出し方: PR

## ドキュメント

- 調査で確かめること: 読者と目的、既存の文書(重複・置き場所・書式)、書く事実の出どころ(コード・仕様・一次情報)
- 完了条件の形: 書いた事実が出どころと合っていること(該当箇所を示せる)、リンク切れが無いこと、ビルドや表示の確認があれば通ること
- 受け入れ検証の観点: 事実の誤り(コード・仕様・一次情報と食い違う記述)、目的に対する抜け、読者がそのまま使えるか(手順が実行できる、用語が定義されている)
- 成果物の出し方: リポジトリの文書ならPR。リポジトリ外ならレポートと同じ

## データ解析

- 調査で確かめること: データの出どころと取得条件、前処理、明らかにしたい問い、評価の条件(真値・ベースライン・除外区間。ユーザーに確認する)
- 完了条件の形: 同じスクリプト・同じ入力で同じ結果が再現できること、結論が数値(と必要なら図)で示せること
- 受け入れ検証の観点: 結論が数値・図から言えるか(言い過ぎていないか)、評価の条件や除外の選び方で結論が変わらないか、前処理やコードの誤りで数値が歪んでいないか
- 成果物の出し方: レポート(図表はArtifact)と再現用のスクリプト。スクリプトの置き場所は方針の承認時に決める

## 調査・技術検討

- 調査で確かめること: 問いと判断の基準(何が決まれば終わりか)、比べる候補、前提となる制約(環境・ライセンス・既存の構成)
- 完了条件の形: 候補ごとの比較が、判断の基準に沿って一次情報(公式ドキュメント・規格・ライセンス本文・実測)付きで揃っていること
- 受け入れ検証の観点: 主張が一次情報で裏付けられているか(推測を断定していないか)、比較が同じ条件で公平か、判断の基準に答えているか
- 成果物の出し方: レポート(比較表・図はArtifact)

## 環境構築・設定

- 調査で確かめること: 今の環境の実測(設定ファイルの中身・配置・所有者・バージョン)、変更の影響を受けるもの(他のツール・既存の設定・他のマシン)
- 完了条件の形: 新規構築と、今の環境からの移行の両方で、意図した状態になること。続けてもう一度流して差分が出ないこと(`testing-workflow`の移行の検証軸)
- 受け入れ検証の観点: 移行で古い設定が残って衝突しないか、既存環境が依存している識別子を変えていないか、元に戻す手段があるか
- 成果物の出し方: 設定を管理しているリポジトリのPR。管理されていない環境なら、手順と結果のレポート

## 発表資料

- 調査で確かめること: 聞き手・持ち時間・伝えたいこと、使う素材(図・数値・既存の資料)とその出どころ
- 完了条件の形: 書き出し(PDFなど)が通ること、持ち時間に収まる分量であること、数値や図が出どころと合っていること
- 受け入れ検証の観点: 主張が根拠(数値・図・一次情報)と合っているか、話の流れが目的に沿っているか、聞き手にとって前提の抜けが無いか
- 成果物の出し方: Slidevのファイル(`~/slides`のワークスペース。記法とコマンドは`~/dotfiles/docs/slidev-cheatsheet.md`)と書き出したファイル。`~/slides`は公開リポジトリなので、業務資料は`decks/private/`(コミットしない)、公開してよいものだけ`decks/public/`に置く。区分は方針の承認時に決める
