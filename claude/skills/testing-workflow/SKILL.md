# Testing Workflow

テストによる検証作業を、ローカル(ユニット/シミュレーション結合)と実機の2つのフローに分けて支援する。`task-execution`が「ローカルテストフロー」を、`task-workflow`が「実機テストフロー」を共通の検証手段として使うほか、検証のみが目的のタスク(最終実機確認など、実装・不具合修正を伴わないもの)自体を扱う独立したジャンルとしても使う。

## 前提

- テストの進め方は、このdotfilesの`~/.claude/CLAUDE.md`の「テスト」節に従う: まずローカルで検証できる範囲を最大化する、テストケースは必要以上に増やさない
- テストコードのpush・PR作成など状態変更操作は、毎回ユーザーの明示確認を得てから実行する(`~/dotfiles/claude/rules/write-approval.md`参照)
- 司令塔のセッション(分業時)ではテストの追加など作業ツリーの編集ができないので、それらは`task-workflow`の「委譲」の作業指示書で実装役に頼む
- 開発タスク(`task-execution`・`task-workflow`)の一部として使われる場合と、独立したタスク(Notion・GitHub Issue・口頭の依頼)として着手する場合とで、後半の扱いが変わる(「完了後」セクション参照)
- 検証手段ごとに検出できない不具合クラスがある。特にdry-run・静的チェックは、書き込みそのものが引き起こす不具合(既存設定との衝突など)を原理的に検出できないため、これらが通ったことを「本実行しても安全」の根拠にしない

## 事前準備

独立したタスクとして着手する場合は、`task-workflow`の「事前準備」(タスクの出どころを決めるところから)を実行する。開発タスクの一部として使われる場合は、呼び出し元ですでに実施済みのためスキップする。

## テスト対象・期待結果の確認

1. 独立したタスクとして着手する場合、タスク内容(取得方法は`~/.claude/skills/task-workflow/references/task-sources.md`)から、何を検証すべきか・期待する結果を把握する
2. 開発タスクの一部として使われる場合は、`task-workflow`の「調査」で把握した期待動作(実装)または再現手順(不具合)を検証対象にし、3以降でテスト方針を立てる
3. 検証範囲(ユニット/シミュレーション結合/実機のどこまで必要か)を確認する。不明であればユーザーに確認する
4. 既存環境(構築済みのマシン・稼働中の設定・既存データ)を変更する作業かを判定する。該当する場合、検証軸を「新規構築」と「現行状態からの移行」の2本立てにする。移行時にだけ起きる不具合(旧設定の残存・新旧定義の衝突など)は、新規構築の検証では通らない経路にある
5. 期待結果が数値的なpass/failで判定しづらい場合(システムの挙動を可視化して良し悪しを判断する必要があるなど)、判断基準をできる限り定量指標(追従誤差・収束時間・逸脱量など)に落とし込めないか検討する
6. 評価の条件(何を真値・ベースラインとするか、どのデータ区間を比較から外すか)は、Claudeが自分で決めずに案を出してユーザーに確認する。現場の事情やハードのスペックはコードからは読めず、条件の選び方次第で結論が変わってしまうため
7. 5で定量化しきれず可視化による判断が残る場合、判断に注目すべきデータ(誤差・軌跡・状態量など)を洗い出し、それを可視化する手段が対象プロジェクトに既存でないか確認する(可視化スクリプト・rviz設定・ロギングツール等)。既存の手段で可視化できない場合は、可視化方法を検討してユーザーに提案する

## ローカルテストフロー(ユニット/シミュレーション結合)

Claudeが自走して実行できる範囲。

1. まず既存のユニットテスト・スタブ/モックを活用してローカルで確認できる範囲を最大化する(`~/.claude/CLAUDE.md`のテスト方針)
2. 既存のテストでカバーしきれない場合のみ追加する。テストケースは必要以上に増やさず、各ケースについてなぜそのケースが必要かを明確にする
3. シミュレーションによる結合テストが必要な場合は、対象のシミュレーション環境で実行する(起動方法は対象プロジェクトのCLAUDE.md/READMEを確認する)
4. 「テスト対象・期待結果の確認」で移行の検証軸を立てた場合、現行状態を推測で作らず実測し(設定ファイルの中身・配置・所有者など)、使い捨て環境(コンテナ等)にシードしてから変更後の手順を流す。意図どおりの状態に収束すること、続けてもう一度流して差分が出ないことまで確認する
5. 挙動を可視化して判断する場合は、「テスト対象・期待結果の確認」で洗い出した可視化手段を使って判断基準の画像(軌跡プロット・誤差の時系列グラフ・rvizのスクリーンショット等)を生成し、Claude自身がその画像を読んで、事前に定めた判断基準に照らして評価する。可能であれば、既知良好な過去の実行結果(ベースライン)と重ね合わせて比較し、単発の目視印象だけに頼らない
6. シミュレーション終了時は、起動した全プロセスが確実に終了したことをプロセス一覧等で確認してから次に進む。`pkill -f`等のデフォルトシグナル(SIGTERM)は子プロセスに伝播せず孤児化して残り続けることがあり、それが次回以降のローカルテストの誤動作(名前衝突など)につながるため、対象プロジェクトの正規の終了手順を使う
7. failした場合、思いつきで別の修正を試さない。「なぜその修正で直らなかったか」を整理する。開発タスクの一部なら、それを報告して不具合の原因の見直しは`task-workflow`の「調査」に戻す(洗い出し済みの候補リストの次点から検証する)
8. 実行結果(pass/fail、ログ、失敗時の原因)をまとめる

## 実機テストフロー

Claudeは実機を直接操作できないため、ユーザーへの依頼という形で進める。

1. 実機での確認に必要な手順(準備するもの、操作手順、確認すべき挙動・出力、安全上の注意点があれば含める)をチェックリストとして整理する
2. 整理した手順をユーザーに提示し、実施を依頼する
3. ユーザーから実施結果(挙動・ログ・数値など)を受け取り、期待結果と照合する
4. 想定外の結果が得られた場合は、その内容を整理してユーザーに報告する。原因調査が必要そうであれば、開発タスクの一部なら`task-workflow`の「調査」に戻ることを、独立したテストタスクなら新規の不具合タスクとして起票することを提案する

## 完了後

1. ローカル/実機それぞれの結果を整理する
2. 開発タスクの一部として使われた場合は、整理した結果を呼び出し元に返す(タスクの記録・成果物の提出は`task-workflow`が行う)
3. 独立したタスクとして着手した場合は、`task-workflow`の「タスクの記録」を実行する。テストコードの追加などpushが必要な変更があれば、続けて同「成果物の提出」も実行する
